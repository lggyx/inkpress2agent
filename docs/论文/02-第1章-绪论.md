# 第1章 绪论

## 1.1 研究背景

写作这件事，工具顺手了才容易坚持。对个人写作者来说，发布文章主要有两条路：用微信公众号、知乎这类托管平台，或者自建博客。托管平台的吸引力在于注册即用、自带流量，但写得久了，一些问题会慢慢暴露出来。排版受平台编辑器的限制，想排个特别的版式很麻烦；数据存在别人服务器上，导出渠道有限，哪天平台规则变了，内容去留自己说了不算；页面样式永远是平台统一的样子，个人风格无处安放。

另一边，Markdown 在技术写作者中已经相当普及。用 Markdown 写作、排版、发布一条龙，注意力可以一直留在内容上，不用被富文本编辑器打断。很多写作者因此向往一个数据自有、样式可定制、支持 Markdown 工作流的个人站点。

博客系统本身并不新鲜。WordPress 占据了全球网站内容管理系统市场的主要份额，Ghost、Halo 等系统也提供了现代化的写作体验。但这些系统大多没有把 AI 能力做进核心功能。2022 年底以来，以 GPT 系列为代表的大语言模型在文本生成任务上达到了可用的水平，国内智谱 GLM、DeepSeek、通义千问等模型也都开放了 API 服务，调用成本已经低到个人开发者可以承受。把润色、摘要、打标签这类机械劳动交给模型，人只负责思考，对每天产出的个人创作者有实际价值。

正是在这样的背景下，本文设计并实现了 InkPress 个人博客与文章管理系统：用主流的企业级技术栈保证系统质量，用可插拔的 AI 适配层把大模型能力接进来，同时把数据所有权还给作者。

## 1.2 研究目的和意义

本课题的目的很直接：为个人创作者做一个真正"属于自己的"博客系统。具体来说有三层。

对写作者，系统提供完整的文章管理与发布能力。草稿、发布、置顶、分类、标签、归档这些基本功能之外，重点是把 Markdown 工作流做顺畅：Vditor 编辑器支持所见即所得，正文中的代码块有高亮，图片有统一的图床外链方案。数据的控制权完全在作者手里，数据库是自己的，随时可以整体迁移。

对开发者，这个项目覆盖了 Java Web 开发的主要环节。Spring Boot 框架搭建、MyBatis-Plus 持久层、MySQL 数据库设计、Redis 缓存、Spring Security 与 JWT 认证、RESTful 接口设计，以及 Vue 3 前端工程化。其中大模型 API 的接入涉及提示词设计、流式响应转发、多服务商适配和超时降级等工程问题，这类问题在课程学习中较少涉及，通过本课题可以完整实践一次 AI 能力的工程化落地。

对毕业设计本身，本课题的工作量适中且边界清晰：功能范围可控，技术栈主流，论文有足够的分析设计内容可写；同时 AI 写作辅助的加入让系统区别于常见的博客类题目，答辩时有自己的特点。

## 1.3 国内外研究现状

### 1.3.1 博客与内容管理系统

国外方面，WordPress 是目前使用最广泛的内容管理系统。根据 W3Techs 的统计，截至 2025 年，WordPress 驱动了全球约 43% 的网站，在全球内容管理系统市场中占比约 60%。WordPress 基于 PHP 与 MySQL，插件生态庞大，但单体架构和同步加载方式在现代前端工程实践中显得偏重。Ghost 使用 Node.js 实现，主打订阅制写作，编辑体验好，但定制主题需要熟悉其模板语言。Hugo、Hexo、Jekyll 属于静态站点生成器，把 Markdown 文章在本地编译成静态页面，访问速度快、维护成本低，缺点是没有后台，评论、搜索等动态功能要依赖第三方服务。

国内方面，Typecho 是轻量的 PHP 博客程序，Halo 使用 Java 开发、采用可插拔架构，近年在中文社区增长较快。

总体来看，现有系统解决了"发布"的问题，但多数项目起步较早，前端仍是模板渲染或混合渲染；对 AI 写作辅助的支持基本停留在插件层面，缺少与编辑器、文章元数据打通的一体化设计。

### 1.3.2 Web 应用开发技术

Fielding 在 2000 年的博士论文中提出 REST 架构风格，此后资源化的接口设计逐渐成为 Web 服务的主流约定。前后端分离架构下，前端通过 HTTP 接口获取 JSON 数据并自行渲染，后端只负责业务逻辑，两端的开发与部署可以独立进行。认证方面，传统 Session 方案在集群环境下需要共享会话存储，基于 JSON Web Token（JWT，RFC 7519）的无状态认证把用户信息签名后放入令牌，服务端不保存会话状态，更适合前后端分离与横向扩展的部署形态。持久层方面，MyBatis-Plus 在 MyBatis 之上提供了通用 CRUD 与分页插件，减少了重复代码。缓存方面，Redis 以内存存储支撑热点数据的高频读取，是缓解数据库压力的常用手段。前端方面，Vue 3 的组合式 API 改变了按选项组织代码的方式，使相关逻辑可以聚合维护，配合 Vite 构建工具获得了较快的开发体验。

### 1.3.3 大语言模型与写作辅助

Vaswani 等人在 2017 年提出 Transformer 结构，以自注意力机制替代循环网络处理序列依赖，成为后续大模型的基础架构。Brown 等人在 2020 年证明，参数量足够大的语言模型可以通过上下文学习在不微调的情况下完成多种文本任务。国内模型方面，智谱的 GLM 系列、DeepSeek 系列、阿里的通义千问系列均开放了 API，且大多兼容 OpenAI 的 Chat Completions 接口格式，这一格式已成为模型服务的事实标准。在写作场景中，生成式摘要可以自动提取文章要点，文本润色可以对表述进行改写优化，关键词抽取可以辅助作者打标签，这些任务都可以通过提示词设计直接调用通用模型完成，不需要训练专用模型。

## 1.4 研究内容

本文围绕 InkPress 系统的设计与实现展开，主要工作包括以下几个方面。

第一，需求分析与系统设计。梳理前台访客与后台管理员两类角色的功能边界，完成总体架构设计、功能模块划分和数据库设计。数据库包含用户、文章、分类、标签、文章标签关联、评论、操作日志七张表，论文中给出了完整的 E-R 图和表结构说明。

第二，系统编码实现。后端实现认证授权、文章管理、分类标签、评论审核、数据看板等模块；前端实现前台阅读页面与后台管理页面。工程上重点解决了几个问题：浏览量采用 Redis 计数加定时回写的方案，避免每次浏览都写库；Markdown 渲染前经过 DOMPurify 白名单净化，防止脚本注入；AI 调用通过适配层封装，切换模型服务商只需修改配置。

第三，AI 写作辅助模块。定义统一的对话模型接口，默认实现 OpenAI 兼容协议，提供润色、摘要生成、标签推荐三项功能，其中润色采用 SSE 流式输出，前端实现打字机效果。

第四，系统测试。编写接口冒烟测试脚本，覆盖认证、文章、评论、点赞、参数边界、AI 降级等场景，并结合浏览器兼容性测试验证系统质量。
