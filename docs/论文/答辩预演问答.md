# 答辩预演问题库（Q&A）

按答辩评委的关注点整理，分五类共 22 问。回答要点均对应论文真实内容，括号内为论文章节索引。

## 一、选题与背景类

**Q1：为什么选这个题目？市面上的博客系统不是已经很多了吗？**

A：选它有两个原因。一是需求真实：我自己长期写东西，托管平台排版受限、数据不在自己手里，想要一个数据自有的站点；二是技术上有锻炼价值，覆盖了 Java Web 开发的主要环节。市面系统多，但把前后端分离技术栈、数据自有、AI 一体化结合起来的轻量方案仍然少见，这是空间所在。（1.1、1.4）

**Q2：系统和 WordPress 这类成熟方案比，优势在哪？**

A：不回避差距——WordPress 生态和插件远比我们丰富，这是十几年积累。我们的优势在三点：数据完全自有，没有平台审核和格式限制；AI 能力是内建的，不是插件拼凑；架构是现代化的前后端分离，代码结构对学习者更清晰。定位是"个人创作者的轻量方案"，不是替代 WordPress。（第 4 章现状对比表）

**Q3：AI 功能是不是就是调了个 API，技术含量在哪？**

A：调 API 是最后一公里，前面还有不少工作。适配层屏蔽了厂商差异，切换只改配置；提示词设计约束输出格式并做容错解析，模型返回不合规时不阻断用户操作；流式输出涉及 SSE 解析、节流写入和中止控制。检索部分更不是调 API——特征哈希向量、混合排序都是自己实现的，实验数据在论文表 6-5。（4.4、5.4、5.5）

## 二、技术深度类

**Q4：为什么用 JWT 不用 Session？**

A：前后端分离场景下，JWT 的无状态特性更适合。服务端不存会话，部署时加机器不用考虑会话共享；令牌里带角色信息，接口鉴权直接读声明。代价是指定后无法主动作废，用 7 天有效期控制风险，个人博客场景可接受。（2.5、5.2）

**Q5：浏览量为什么要绕这么一大圈，直接写数据库有什么问题？**

A：直接写库的话，热门文章被频繁打开会把数据库压垮，这是典型的高频写问题。方案是 Redis 原子自增承接每次浏览，定时任务每分钟把增量批量合并进 MySQL。本质是用一分钟的一致性窗口换性能，进程崩溃最多丢一分钟增量。（5.3 节，图 5-2）

**Q6：浏览量回写周期内数据库是旧值，用户看到的是新值，这不算数据不一致吗？**

A：是"最终一致"，不是"强一致"。读者看详情页读的是 Redis 计数，体验不受影响；管理端列表排序这种对实时性要求不高的场景，一分钟延迟无感。如果业务要求强一致，比如金融计数，这个方案就不适用，会改成写库加缓存失效。（6.2 节 B-07 用例）

**Q7：本地特征哈希向量和商用 Embedding 差距大吗？为什么选它做默认？**

A：差距客观存在，商用模型有语义泛化，本地哈希没有，字面重合度低的查询效果会差。选它默认的理由：零依赖、零成本、毫级响应，开发和无密钥环境下功能完整可用；而且向量实现是可插拔的，配置 Key 后自动切远程，业务代码不动。论文表 4-1 有三个方案的对比。（4.4.1）

**Q8：混合排序的 0.85 和 0.15 是怎么定的？有理论依据吗？**

A：有实验调整的成分。语义承载"相关"的主要含义所以给高权重，标签负责把同系列文章聚拢所以给低权重。这两档是试出来效果可接受的组合——推荐结果的准确率和多样性在这个比例下都不错。论文里如实写了这是经验权重，没有包装成理论最优。（4.4.3）

**Q9：RAG 怎么保证模型不编造？**

A：三道防线。提示词硬约束"仅依据提供的资料回答，资料不足就明说"；检索结果为空时直接不调模型，返回"站内暂无相关内容"；回答附引用来源，读者可以点回原文核对。前两道防幻觉，第三道让答案可验证。（4.4.4、5.5.3）

**Q10：SSE 断网了怎么办？为什么不用 WebSocket？**

A：断网时前端 fetch 会抛错，走 onError 分支提示用户。选 SSE 不选 WebSocket 的理由：AI 输出是单向的，服务端推给客户端就够了，不需要全双工；SSE 基于普通 HTTP，实现和调试都简单，Nginx 代理关掉缓冲即可。（5.4 节）

## 三、工程实践类

**Q11：数据库七张表是怎么定的？有没有冗余设计？**

A：按功能实体划的：用户、文章、分类、标签、文章标签关联、评论、操作日志。冗余上有一个取舍：浏览量、点赞数作为计数字段直接放文章表，没有拆计数表。因为个人博客规模下没必要，而且 Redis 已经挡掉了高频写。这个取舍在论文里说明了。（4.3.2）

**Q12：文章删除是物理删除，如果误删了怎么办？**

A：目前是物理删除，靠删除前的确认对话框防误触。答辩后可以考虑加软删除，加个 deleted 标记位，查询时过滤即可，改动不大。这一点写进了论文的不足部分。（8 章）

**Q13：测试是怎么做的？26 项冒烟覆盖了什么？**

A：分三个层次。冒烟脚本 26 项断言覆盖接口层：认证、文章流转、评论审核、点赞去重、参数边界、检索推荐、AI 降级，每轮代码改动后都跑，拦下过几次回归问题。功能测试 31 项走完整用户路径。检索单独做了实验，五组查询 Top-1 全命中。（6.2-6.4）

**Q14：怎么保证代码质量？遇到最难的问题是什么？**

A：质量上靠分层清晰、统一响应结构、全局异常处理和每轮的冒烟回归。最难的是 SSE 流式那块——前端解析 data: 前缀时按规范要消费一个可选空格，漏掉这个细节，润色正文每段开头都会多一个空格，查了一下午。这类坑都记在论文 5.4 节。（5.4）

## 四、数据与效果类

**Q15：站内 38 篇文章是哪来的？真实用户用过吗？**

A：38 篇是从我原来 GitHub Pages 博客导入的历史文章，用脚本批量转换，图片转为外链。功能测试用的就是这些真实数据，包括长文章、多图文章。目前主要是自己和身边同学在用，评论功能有真实互动数据。（1.4、6.2）

**Q16：检索实验只有五组查询，样本是不是太少？**

A：承认五组是小样本，主要验证方案可行性。论文里写了后续计划：把查询集扩充到 15 组以上，并做本地向量与远程 Embedding 的对比评测。五组的结果趋势是清晰的——字面重合度高的查询分数明显高，这与特征哈希的原理一致，反过来印证了方案特性。（6.3、8 章）

## 五、展望与反思类

**Q17：系统还有什么不足？**

A：三处。AI 功能依赖外部服务，网络波动时体验受影响，后续加请求队列和重试；本地向量精度有上限，值得做量化对比实验；操作日志只记了管理端，访客侧异常访问还没采集。（8 章）

**Q18：如果继续做，下一步做什么？**

A：两个方向。语义搜索接入前台搜索框，检索实验扩充后做系统评测；RAG 从单轮扩展到多轮对话，结合会话历史做指代消解。这两个都不推翻现有架构，适配层和向量服务留了扩展空间。（8 章）

**Q19：做这个项目最大的收获是什么？**

A：不是技术栈本身，是解决问题的思路。以前遇到问题先问人，现在先查官方文档、看源码、写最小复现。像 jjwt 0.12 的 API 变化、MySQL 字符集乱码这些坑，都是这样一个个踩过来的。（结语部分）
