# 第2章 相关技术介绍

## 2.1 Spring Boot 框架

Spring Boot 是 Spring 家族中使用最广泛的快速开发框架。它在 Spring 之上提供了自动配置机制：根据 classpath 中引入的依赖，自动装配数据源、Web 容器、安全框架等基础设施，开发者通过 application.yml 中的少量配置即可覆盖默认行为，"约定优于配置"的理念显著减少了样板代码。

本系统使用 Spring Boot 3.3.5，要求 JDK 17 及以上。引入的主要 Starter 包括：spring-boot-starter-web 提供内嵌 Tomcat 与 Spring MVC；spring-boot-starter-data-redis 提供 RedisTemplate 操作缓存；spring-boot-starter-security 提供认证与授权框架；spring-boot-starter-aop 支持面向切面编程，用于操作日志记录。此外，spring-boot-starter-validation 提供了基于 Jakarta Validation 的参数校验能力，本系统中文章保存、评论提交等接口的入参约束都通过注解声明。

Spring Boot 的自动配置并非黑盒。以 MyBatis-Plus 为例，引入 mybatis-plus-spring-boot3-starter 后，框架自动创建 SqlSessionFactory 并扫描 Mapper 接口，开发者只需在启动类上添加 @MapperScan 指定扫描包路径。这种"引入即用、按需覆盖"的模式，让本系统把精力集中在业务逻辑而非环境搭建上。

## 2.2 Vue.js 与组合式 API

Vue.js 是一套用于构建用户界面的渐进式 JavaScript 框架。Vue 3 最大的变化是引入了组合式 API（Composition API），与 Vue 2 的选项式 API 按 data、methods、watch 等选项组织代码不同，组合式 API 允许把同一个功能的响应式状态、计算属性、方法和生命周期钩子聚合在一个 setup 函数或自定义组合函数中。

本系统的前端页面大量受益于这一特性。以文章编辑页的 AI 润色功能为例，它涉及请求发起、SSE 流解析、节流写入编辑器、中止控制四件事，在组合式 API 下这些逻辑集中在一个函数内，代码从上到下即可读完，没有跨选项的隐蔽耦合。后台管理页面中，数据看板的 ECharts 初始化和窗口尺寸自适应也被封装为独立的组合函数。

构建工具选用 Vite。开发模式下 Vite 基于浏览器原生 ES Module 提供按需编译，修改代码后热更新几乎是即时的；生产构建使用 Rollup 打包并做 Tree Shaking。本系统前端还使用了 Pinia 做状态管理（存储登录态与用户信息）、Vue Router 做路由管理（含管理员角色的路由守卫）、Element Plus 组件库、Vditor Markdown 编辑器、marked 与 DOMPurify 渲染正文、highlight.js 做代码高亮。

## 2.3 MySQL 数据库

MySQL 是最流行的开源关系型数据库，本系统使用 8.0 版本。选用关系型数据库的理由很实际：博客系统的数据结构稳定且关联关系清晰——文章属于分类、文章关联多个标签、评论挂在文章下，用外键和关联表表达这些关系比文档型数据库更直观，事务支持也保证了如"删除文章同时清理关联"这类操作的原子性。

MySQL 8.0 在性能上也有对本系统有用的改进。窗口函数和公用表表达式让复杂统计查询更容易书写，本系统数据看板的分类文章数分布就用了一条带条件的 GROUP BY 聚合查询。字符集方面，建库时统一使用 utf8mb4，避免 Emoji 和特殊符号存储时出现乱码——这一细节在开发过程中真实踩过坑：数据库初始化脚本首次执行时客户端字符集设置不当，导致中文描述列出现乱码，后来通过在脚本开头增加 SET NAMES utf8mb4 彻底解决。

## 2.4 Redis 缓存

Redis 是内存键值数据库，本系统使用 7.x 版本，主要承担三类职责。

热点数据缓存。首页的热门文章列表按浏览量排序，是全站访问频率最高的数据之一。系统将查询结果序列化为 JSON 存入 Redis，设置五分钟过期，读请求优先命中缓存，避免每次访问都做数据库排序查询。

计数与去重。文章浏览量是典型的高频写入数据：每打开一次详情页就要加一，如果直接写数据库，热门文章会把数据库打满。系统采用 Redis 原子自增（INCR）承接浏览计数，同时把文章 ID 写入一个"脏集合"标记待回写，定时任务每分钟把增量批量合并进 MySQL。点赞去重则利用 Redis 集合：同一访客（登录用户 ID 或客户端 IP）对同一文章只能点赞一次，集合的天然去重特性让判断只需一次 SADD 的返回值。

会话外的辅助存储。Redis 的序列化方式在系统启动时统一配置：Key 使用字符串序列化，Value 使用 JSON 序列化，兼顾可读性与兼容性。

## 2.5 JWT 认证技术

JWT（JSON Web Token，RFC 7519）是一种紧凑的令牌格式，由 Header、Payload、Signature 三段 Base64URL 编码组成。Payload 中可以携带用户标识、角色等声明，Signature 使用密钥对前两段签名，服务端只需验证签名即可确认令牌未被篡改，不需要在服务端存储会话。

本系统使用 jjwt 0.12 实现。登录成功后，服务端签发包含 userId、username、role 的令牌，有效期七天。每次请求经过 OncePerRequestFilter 过滤器，从 Authorization 头解析令牌，验证签名后构造无状态的认证主体放入 SecurityContext。管理端接口通过 SecurityConfig 的请求匹配规则限定为 ADMIN 角色，未携带有效令牌的访问统一返回 401 JSON，角色不足返回 403。

无状态认证换来的是部署的灵活性，代价是令牌签发后无法主动作废。对于个人博客这类场景，把有效期控制在七天是可接受的折中。此外开发中有一个细节：HS256 签名算法要求密钥长度至少 32 字节，测试环境的短密钥会在初始化时报错，这一点在部署文档中作了说明。

## 2.6 大语言模型与 SSE 流式传输

本系统的 AI 写作辅助基于大语言模型 API 实现，不涉及模型训练。当前主流模型服务商（OpenAI、DeepSeek、智谱、通义千问、Kimi 以及本地部署的 Ollama）都提供了兼容 OpenAI Chat Completions 格式的接口，这一事实标准让适配工作大为简化：系统只需按该格式构造请求体（模型名、消息列表、温度参数、是否流式），用 Bearer 令牌鉴权，即可对接不同厂商。

提示词设计是 AI 功能的核心。以润色为例，系统提示词要求模型"保持原意与整体结构，修正错别字和语病，直接输出润色后的全文，不要任何解释或前缀"，并支持用户追加自定义要求；摘要生成则限制在 80 至 150 字并要求直接输出正文；标签推荐要求返回 JSON 数组以便程序解析，并对解析失败做了容错——返回空列表而不阻断保存流程。

流式输出采用 SSE（Server-Sent Events）。AI 润色如果等模型生成完再返回，用户要盯着空白页面几十秒；SSE 让服务端每收到一段增量就推送一次，前端累积渲染，形成打字机效果。实现链路上：后端通过 Java 11 的 HttpClient 读取上游流式响应，逐行解析 SSE 数据块，提取增量文本后通过 Spring 的 SseEmitter 转发给浏览器；前端用 fetch 加 ReadableStream 手动解析事件流，累积后节流调用编辑器的 setValue 方法，避免高频重绘。

## 2.7 开发环境

本系统的开发与运行环境如下。

后端方面：开发工具为 IntelliJ IDEA，构建工具 Maven 3.9，运行环境 JDK 17，测试环境 JDK 21；单元测试与接口测试使用 JUnit 5 与 Postman，接口文档通过 Knife4j 自动生成。前端方面：编辑器为 VS Code，Node.js 20+，包管理器 npm，浏览器测试覆盖 Chrome 与 Edge 最新版本。数据层：MySQL 8.0 与 Redis 7 均通过 Docker 容器运行，保证开发环境与部署环境的一致性。版本控制使用 Git，代码托管于 GitHub 私有仓库。
