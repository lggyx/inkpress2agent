## 1. 选题背景及研究的目的和意义

### 1.1 选题背景

开发者在平时学习和做项目的过程中，习惯把调试经过、配置方法和踩到的问题整理成技术博客，方便日后翻查，也能给别人提供参考。发布渠道方面，多数人选择知乎、掘金、CSDN、微信公众号这类第三方平台，看中的是平台流量和现成的读者群体。但麻烦也随之而来：文章托管在平台的服务器上，管理权并不在作者手里，平台策略一旦调整，文章可能被下架甚至误删，作者很难有申辩的余地。

写作技术博客是开发者整理经验的常用方式，而目前文章大多发布在第三方平台上。平台的流量优势明显，但文章的存储和展示都受平台规则约束：Markdown 原文件一般不能批量导出，本地备份只能逐篇复制；代码块贴进富文本编辑器后格式容易错乱；外链图片还会被防盗链拦截。文章需要在多个平台同步时，手动调整格式的工作量很大。解云菲与万波[1]在信息管理系统研究中指出，构建数据自主可控、功能完备的管理系统，是保障数据安全与自主管理的关键举措。

这些问题可以靠自建博客解决，但现有的开源方案并不都能满足需要。WordPress 功能全面，但架构重、插件多，也出现过安全事故，例如 CVE-2024-4577 远程代码执行漏洞；Hexo 和 Hugo 生成静态页面，体积小、速度快，但没有在线编辑后台，评论功能要另外接第三方服务；国内的 Halo 支持基本的动态功能，不过对大语言模型辅助写作和自动分发还没有提供支持。与此同时，大语言模型的使用条件这几年改善了很多，智谱 GLM 和 DeepSeek 都开放了价格较低的 API，SSE 和 Playwright 也是成熟工具，因此自己开发一套博客系统在技术上是可行的。

### 1.2 研究的目的和意义

#### 1.2.1 研究目的

这个课题要做的东西说直白些：一套自己说了算的博客系统，Spring Boot 加 Vue，前后端分离。功能不贪多，全围着写作流程转——文章用 Markdown 在本地写、本地存，数据落自己的库；写的时候有大模型流式辅助；写完草稿自动推到各平台，省去挨个排版的重复劳动；再配上树状评论和站内检索，阅读端的基本体验就齐了。为什么挑这五块？对着的就是前文那三类痛点：数据在别人手里、排版重复劳动、开源系统跟不上新的写作习惯。归结成一句话，让技术作者有自己的地盘，写和发都利索。

#### 1.2.2 研究意义

理论意义：本课题把前后端分离架构思想、分布式检索理论和大语言模型应用技术放到同一个单机部署场景里做整合设计，在硬件资源有限的前提下处理模块分层解耦与服务可用性问题；检索部分采用 BM25 关键词通道与稠密语义向量（Dense Vector）通道并行、倒数排名融合（RRF）算法合并排序的方案，其调优机制和实际检索效果会结合实验数据验证，结论可供同类中小型内容检索与管理系统的架构设计参考。

现实意义：真用起来，好处落在谁头上很清楚。写文章的人最直接：数据和发布流程都回到自己手里，平台改规则不再左右自己的内容；润色、摘要、多平台草稿填充这些重复活交给系统，省下的时间都是自己的。读者也能感觉到变化——前台服务端渲染（SSR），首屏快；站内检索可用，找技术资料不用一篇篇翻历史文章。维护的人则省心：无状态 JWT 认证，部署轻，好维护，开销压得低。

## 2. 国内外在该方向的研究现状及分析

### 2.1 国外研究现状及分析

国外在内容管理系统方向起步较早，WordPress 目前支撑着全球约 40% 的网站（W3Techs 统计）；随着 Web 技术向单页面应用（SPA）演进，Ghost 以及 Medium、Substack 等在线写作平台也相继出现。REST 架构风格由 Fielding[2] 提出，是现代 Web 服务无状态交互和前后端分离的基础。大模型出现之后，国外工具的迭代更快：Vaswani 等[3]提出 Transformer 架构、Brown 等[4]研究少样本提示学习以后，Notion AI 等写作辅助工具开始普及。

不过国外这套东西搬进国内博主的日常，水土不服马上显出来：服务器在境外，访问延迟高，数据出境还附带合规顾虑；Ghost、Medium 们对接的是 Twitter、WordPress，公众号、知乎、掘金、CSDN 各家的排版格式和接口规范它们根本不适配；AI 写作多是弹个窗对话，跟本地 Markdown 编辑、草稿存储完全不搭，写和排两个环节是断开的。

### 2.2 国内研究现状及分析

国内的技术内容生态明显向平台聚集：微信公众平台、知乎、掘金、CSDN 上有大量开发者与技术读者，同一篇文章多发几个平台来扩大影响力是创作者的普遍做法。工程模式上前后端分离已成主流，王晓峰与李晨[5]的研究表明 Spring Boot 结合 Vue 分层清晰、前后端协同效率高，可维护性和扩展性都好。就本课题的几项关键技术而言，国内也有相应积累：张宇与陈浩[6]研究了大语言模型加 SSE 协议做实时流式写作辅助的可行性，刘伟与赵敏[7]把 Elasticsearch 倒排索引与稠密向量组合成混合检索，专业术语匹配和语义理解的查询准确度都有改善，孙健与黄志成[8]的实践则说明 Redis 缓存加防刷限流确实能支撑高并发场景的稳定性。

再看开源博客这个具体形态，短板更实在：多数系统只管把文章发出来、管起来，大模型 API 的统一接入、提示词编排没有专门设计，长文本辅助想稳定都难；发完文章还得手动逐平台复制调格式，自动化在这一步是缺位的；站内搜索基本还是 SQL LIKE 模糊匹配，分词糙，语义检索谈不上。这个课题就是冲着这几处空缺来的——做一个集 Markdown 编辑、国产大模型辅助写作、跨平台排版分发、全文混合检索于一身的个人技术博客系统。

## 3. 研究内容

本系统面向技术创作者与普通读者，设计并实现一个功能完善的个人博客系统，划分为以下五个功能模块：

### 3.1 个人中心与身份认证模块

用户注册与登录验证：密码不能明文存——BCrypt 加密后入库（参考杨帆与郭鹏[9]的分布式认证模型）；登录成功签 7 天有效的 JWT 无状态令牌，后端拦截器统一校验，越权访问直接挡下。

个人信息维护与消息通知：资料、联系方式、头像，用户自己改；有新评论或回复，站内先亮未读提示，SMTP 再往绑定邮箱推一封提醒，两边都不漏。

### 3.2 博客文章管理与交互模块

Markdown 在线编辑与发布管理：编辑器使用 Vditor，支持语法高亮、数学公式渲染和本地图片拖拽上传；系统会定时保存草稿，发布、置顶、软删除等功能也在管理页面里完成。

文章分类与存储适配：分类采用多级树形结构，标签与文章之间是多对多关系；文件存储部分抽象出统一的接口，可以按照配置在本地磁盘和七牛云 OSS 之间切换。

评论互动与高频访问计数：评论分为两层，发布前先经过敏感词过滤；浏览量和点赞的统计频率高，由 Redis 的 INCR 命令在内存里完成计数，避免大量并发写操作直接落到数据库。

### 3.3 AI智能写作辅助模块

文本润色与语法纠错：前端通过 Server-Sent Events（SSE）与后端保持长连接，后端调用大语言模型 API，把结果以流式的方式逐字返回，作者可以边写作边查看修改建议。

文章摘要与标签生成：后端先解析正文，再调用大模型接口生成摘要，用在文章列表和 SEO 展示上；标签则从正文中提取 3 到 5 个关键词，直接推荐给作者。

内容续写与标题推荐：续写根据作者提供的段落提纲进行，由大模型完成；标题也会结合正文的主要论点生成几组备选，供作者比较后选用。

### 3.4 跨平台自动化辅助分发模块

多平台排版格式转换：公众号、知乎、掘金、CSDN 对排版的处理规则不相同，人工逐一调整费时费力，解析器按照目标平台分别做转换，覆盖代码块样式、行内强调和外部链接的展示。

草稿自动同步填充：这一步使用 Playwright 驱动本地浏览器（方案参考了周建国与郑波[10]关于无头浏览器的研究），读取浏览器里保存的登录状态，把排版好的内容填入各平台的草稿箱。

分发记录与外链保存：系统记录每次分发的时间、目标平台和执行结果；文章在平台正式发布后，再把外部链接补录进来，方便以后查找。

### 3.5 站内混合检索与安全运维模块

关键词与向量混合检索：Elasticsearch 8.x 打底，IK 分词管中文，向量进 dense_vector 字段，RRF 把关键词命中和语义相似度合成一个排序——专业术语查得准，语义相关也召回得回来。

访问安全与系统监控：评论先过滤敏感词，恶意刷请求的用 Redis 令牌桶限流；每条请求在入口就打上 traceId（Logback 落日志），出了问题顺着标识就能找到调用点；服务健康度由 Spring Boot Actuator 实时暴露。

## 4. 拟采取的研究方法和技术路线

### 4.1 研究方法

#### 4.1.1 文献研究法

文献研究分两部分进行：一部分是方向性文献，包括 CMS、前后端分离、大模型应用集成和检索算法相关的期刊论文、学位论文和技术文档；另一部分是开源项目，主要分析成熟博客系统的分层方式、数据库设计和安全机制。这些材料最终用于确定本系统的技术选型和模块划分。

#### 4.1.2 需求分析法

需求从创作者的真实操作里来：写文章、转格式、发多平台三个环节逐个调研；读者、博主、管理员三类的业务范围和权限边界划清楚；最后用 UML 用例图、时序图、业务流程图把功能规格和数据交互定下来。

#### 4.1.3 架构设计与数据建模法

系统分为 Controller、Service、Mapper 三层，层间边界按高内聚低耦合的原则划分，外部服务的对接单独封装成适配接口。数据库先做 MySQL 概念结构设计，再依据关系规范化理论转换为物理表结构；索引按查询场景建立，缓存和消息队列的位置在设计阶段一并确定，兼顾读写效率与数据一致性。

### 4.2 技术路线

#### 4.2.1 后端架构

后端以 Spring Boot 3 为主体，数据访问交给 MyBatis-Plus；MySQL 8.0 存用户、文章、系统配置这些结构化数据；热点缓存和原子计数给 Redis 7.x，数据库并发压力小一大截；异步的活——缓存同步、邮件发送——丢给 RabbitMQ，可靠投递照丁浩与袁明[11]的方案做，最终一致性有底。

#### 4.2.2 前端架构

前端和后端各走各的。前台用 Nuxt 3，看中 SSR 和 ISR——搜索引擎收录和首屏速度都受益；组件怎么拆、响应式怎么组织，参考了霍春阳[12]关于前端框架响应式系统与组件化设计的论述。后台是 Vue 3 加 Element Plus，写作界面用 Vditor 做成双栏，左边写，右边同步看。

#### 4.2.3 智能辅助与分发

大语言模型 API 由服务端经 HTTP Server-Sent Events（SSE）长连接对接，内容边生成边返回；多平台分发工具以 Node.js 和 Playwright 驱动本地浏览器，复用登录状态凭据，把本地 Markdown 草稿填入目标平台保存，人工复制排版的环节基本省去。

#### 4.2.4 检索与安全

站内搜索交给 Elasticsearch 8.x：中文分词由 IK 分词器完成，语义特征存入向量字段，文本匹配得分与语义相似度经互惠排序融合算法（RRF）合成最终排序；安全方面用 Spring Security 配无状态 JWT 完成认证与接口鉴权；日志由 Logback 记录，traceId 在请求入口生成并沿调用链传递，异常排查沿它展开。

### 6.1 已具备的条件

## 7. 研究过程中可能遇到的困难和问题，解决的措施

### 7.1 大模型流式调用与网络异常处理

- 问题：大模型 API 属于外部服务，调用时会受到网络波动、接口超时和返回格式异常的影响，这些都会中断 SSE 连接，使页面内容停在半途。
- 解决措施：在后端配置合理的超时与重试，对 SSE 数据帧逐帧校验并捕获异常；前端用接收缓冲区按序渲染，提供取消与重新生成功能，中断后可以立即重试，避免内容停在半截。

### 7.2 跨平台富文本格式差异与页面元素变动

- 问题：平台们的富文本编辑器对 HTML 的支持五花八门，平台一改版，脚本里写死的选择器就可能失灵——排版乱了事小，填充直接失败事大。
- 解决措施：Markdown 先转标准 HTML，再按平台改写标签，两步走；定位元素时文本、层级、相对定位混着用，加上等待重试；真自动化不了就退回剪贴板手动粘贴。

### 7.3 关键词精确检索与语义检索的平衡

- 问题：关键词方式处理不了同义词与模糊表达，纯向量方式查函数名、变量、错误代码这类精确目标时命中率又不足，两条路线各有短板。
- 解决措施：关键词检索与稠密向量检索同时保留，前者经 IK 中文分词处理（标题与正文粒度不同），代码部分直接精确匹配，后者负责语义召回；两路结果用倒数排名融合（RRF）合并排序，融合参数由典型测试用例调试，代码专名要查得准，语义相近的文章也要能召回。
